# 关于同济大学自瞄的开源报告
    这里是浮洲湿地战队2025级算法组队员朱彦。此次报告是对Super Power战队SP_VISION_25（以下简称sp）自瞄部分的开源报告。事先说明，本人作为一个没有做过相应完整项目的视觉成员，从该项目中学习到的点是很多的，我觉得很宝贵的知识可能在大佬眼中只是很平常的点。但鉴于本人能力有限，请各位见量。

## 程序设计上的优点
    1.不同于我们战队的自瞄算法（也就是基于陈君的算法框架），能明显看到sp算法采用的是更加模块化的编程。甚至为单个矩阵运算，卡尔曼滤波运算等提供了单个工具包。所有模块进行封装化，调用起来更加便利
    2.SP的项目没有用到ROS2,而是把所有的信息都放在了yaml文件下。这也是我第一次了解到这种写法。这样在更改参数后就不需要重新编译了。
    3.关于PnP的优化（这点有待确定）：SP在pnp解算中引入了yaw优化，那利用这个进行重投影误差的运算，就可以更准确地判定出装甲板的实际倾斜角度。

## 程序运行结构
    总体来说，经过的程序应该是
    armor定义 -> detector(传统) / MultiThreadDetector（YOLO） -> solver(pnp) -> target(EKF的解算以及输出预测位置) -> tracker ->aimer -> shooter
    
### armor    
    同我们目前的定义一样，SP在armor.hpp,cpp中定义了装甲板的参数.不同的是，它把置信度，在云台与世界坐标系下的xyz，ypr，ypd坐标都归进了类里。实现一个装甲板的完整信息的封装。
    
### detector
    这个文件就是通过传统方式，检测出灯条并匹配成装甲板。当然，由于yaml的配置，所以threshold这些参数也一并写在yaml里面了。

### multithread
    （我之前没有学习使用过openVINO，这是我需要提升的点）不同于我们队内自瞄使用的同步推理方式，SP算法提供的是异步推理。这是我疑惑的点，明明异步处理不会阻塞，为什么我们队选择了同步处理？

### solver
    从solver开始，sp开始使用Eigen来进行运算了。这是本小菜第一次学习这个，所以也来提一嘴。不同于opencv矩阵运算（运用函数，传参形式）虽然要引入Eigen库，以及cv2Eigen以及Eigen2cv的转换，但引入Eigen直接用+，*等来进行矩阵的运算，对代码的可读性有了极大的提升。更关键的是，如果有潜在的计算问题或格式问题，它会在编译是直接报错。这对比以前用opencv运行时才报错，真的有很大的优越性。
    sp在进行pnp解算时，有个最亮眼的地方就是它对旋转向量转矩阵，转弧度等都有相应工具的封装使用。所以也不需要看代码，直接调用即可。个人比较喜欢这点。

    sp计算重投影的方式也很有意思。首先先读取自身机器人云台相对里程计（也就是世界坐标系）的yaw值。又由于已经识别到的装甲板应该在这个范围正负x间（这里取了70）然后让算法从+-区间开始依次迭代，寻找最小的重投影误差。

### tracker
    作为跟踪装甲板的跟踪器，sp使用yaml的特性使得其需要在yaml文件内写入敌方颜色、连续检测多少帧才进入tracking状态、短暂丢失多少帧后才彻底丢失。这些参数当然也是可以自行调节的。
    在本文件中，为了解决装甲板跳变等问题，引入了标准的状态机state_machine。在初始状态下，默认处于lost。在检测到装甲板后，变为detecting，并默认记为1.在到达给定的计数后，进入tracking。

    这里有个保护机制我第一次学习 
    if (state_ != "lost" && dt > 0.1) {
    state_ = "lost";
    }
    即当相机离线（dt时间过长时），我们就强制把状态变为lost。

    而sp也是优先选择距离图像中心最近的装甲板。sp在这之后还引入了优先级，可以自行进行选择（在decider.cpp）中有示例。
    一个有意思的点在于，sp还有一个全向感知相机，如果在检测到更高优先级的目标，会把自瞄的状态切换为switching。
    

### target
    sp在这里使用了11维的状态向量。依次是x,vx,y,vy,z,vz,a,w,r,l,h.其中r,l,h依次为长短轴的半径，以及装甲板的高度差。（本人之前自己写的程序没有考虑这几个怎么算，在这里sp也是给出了相应的方法）这三值也被放入估计，让EKF自行去收敛。
    sp在这使用的也是匀速模型，可能在rm赛场上用匀速就够了。（我以前考虑过用混合多模型的方法，但对算力的要求也确实进一步提高了）

    代码中需注意在夹角求和时，由于可能角度越来越大，sp在工具里封装了一个limit函数进行限制。简而言之就是可以把角度限制在-pi到pi之间。

    个人受益最大的是在装甲板是否跳变的具体实现上。具体来说，我们在第一帧的时候，如果检测到了装甲板，我们就把其定为0号（因为在具体使用时，tracker的set_target函数只会传入一个装甲板，所以不会出现一帧内有多个0号装甲板的情况）而又根据EKF计算的是机器人的质心位置，我们根据编号，就可以相应的计算出四块板的空间xyza四元位置。此时我们计算距离相机最近的三块装甲板（这样就可以过滤调后面的装甲板）。并在下一步取得与预测角度偏差最小的那一块装甲板。此时再根据其id（id在之前确定了就不会再改变了）确定是否产生了跳变/切换。之后在把这块装甲板送入更新步骤，进行EKF跟踪。

### aimer
    在aimer内，实现了弹道解算与角度输出，以及关键的选板策略。这里的参数调节主要是来临角、离去角、敌方高速小陀螺时的发弹延迟、低速时延迟、以及高低转速的切换值。而在目标高速旋转时，由于需要更多的提前量，所以延迟时间也更长。

    sp中把future定义为发弹时刻，弹道解算使用的是不考虑空气阻力的模型。值得注意的是，sp在里面使用了一个迭代10次飞行时间的方法。具体来说，就是现预测目标在子弹到达（future+fly_time）的位置。之后在该位置重新选择瞄准点并求解弹道，给出新的飞行时间。直至飞行时间收敛（个人觉得，这也就相应减少了不考虑空气阻力所带来的影响）
    最后计算出yaw与pitch的值即可。

    在选板逻辑上，sp另装甲板朝向与相机视角为delta_angle。当其为零时，说明其正对相机。
    当装甲板未跳变时，直接锁定id=0的即可。而在低转速情况下，我们只选择delta_angle在+-60度内的装甲板。
    还有个很细节的点，就是sp考虑了一个当目标以45度面向相机的情况。这是有可能出现两块装甲板位置差不多，云台在两块之间连续跳跃。因此，它写了一个锁定的机制。
    而对于小陀螺，我们的策略就像是打它进入时的装甲板。

    当然，sp还提供了一种planner，也就是轨迹规划器。它在+-0.5秒内生成100个点的参考轨迹，利用ADMM算法分别计算出yaw和pitch的控制序列。由于时间有限，算法部分我没有详细的去理解，不过这是一个很好的思路。

## 收获
    毋庸置疑，看济瞄最大的收获就是完全另一套视觉框架的编写方式。与我们战队基于ros节点的开发，sp用yaml配置文件的方式在编译上提供的便利让我印象深刻。
    当然，还有就是Eigen这一工具的使用，相较于opencv，它提供的矩阵运算，真的算的上是简单明了了。
    在编写思路上，模块化的编写方式也让每一步更细，提供了一种新的编写思路。
    当然，还有一些算法上的新点我以前没注意过。比如pnp解算时yaw的限制，特殊情况下锁定yaw，飞行时间迭代，轨迹规划器的原理.....这些新的算法在后续搭建我们队内自身框架的时候也是一个值得借鉴的点    

## 思考
    诚然，sp的模块化有很多特点。但在阅读时，也可以发现其实有些模块的耦合性特别高。像target和aimer板子状态的判定，由于文件直接分开，导致你刚入手时你得反复在这两个文件中进行切换（当然，这应该也是我的能力问题）

    细节方面，sp在火控程序内直接用tolarence预定值直接限定死了，没有动态调节。如果我们队用的动态调节更好，可以考虑进行修改。

    下赛季由于前哨站装甲板变成上下的了，在卡尔曼滤波这一块，我们可以考虑也加上h这个偏差值。使得在反推装甲板时可以让位置更加准确。

    还有就是关于装甲板尺寸的问题。这赛季只有英雄还拥有大装甲板，我之前也一直在想我们是不是可以简化装甲板类型的相关判断，只用数字判断即可。只需要在需要相关尺寸计算的时候多一个枚举类即可。
